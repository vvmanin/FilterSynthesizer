## 3. New findings

### 3.1 §4.2 (BP auto-pairing exception) is not a wide-band-only case

The `min() arg is an empty sequence` exception now reproduces with three designs:

- `BW_BP_n1_50-2500Hz_g2_abs` (pinned)
- `CH_BP_n1_100-2000Hz_g2_a0.1_abs`
- `CH_BP_n1_1-5kHz_g2_a0.5_abs`

All are **order 1 + *Enable 3rd-Order Sections* on**. The trigger is that the
BP transform of the single prototype pole yields two *real* poles. With
*absorb* off the same designs do not crash but lose a pole (§3.2).

### 3.2 `lost_pole`: the trigger is the effective bandwidth, not the nominal band

`lost_pole` rose 28 → 66 designs (all Bandpass; 48 without absorb, 18 with).
The 10-02 report described it as wide-band only (B/f0 ≳ 1.5). The full run
contains a narrow-band case:

- **`CH_BP_n1_10-15kHz_g1_a0.1`** (Chebyshev BP, n = 1, 10–15 kHz,
  α = 0.1 dB, gain 1, absorb off). B/f0 is only 0.41, but the n = 1 Chebyshev
  prototype pole for α = 0.1 dB sits at 1/ε ≈ 6.6 × the α-edge. So the
  −3 dB bandwidth is ~6.6× wider and the two BP poles are real
  (−34.6 k and −171 k rad/s). The pairer keeps one pole in a single
  1st-order stage. Result: shape error 28 dB, gain error 106 dB,
  `gain_extreme` 2·10⁵.

Every n = 1 BP design in the run whose poles came out real is either
`lost_pole` (absorb off: 9 of 44 n = 1 BP designs; Chebyshev, Bessel and
Equiripple-delay classic) or an app exception (absorb on: 3 designs). All 32
n = 1 designs with complex poles are clean. The Custom H(s) gate
("Bandpass with ≥ 2 real poles") would refuse these. The regular responses
have no such gate, so the condition for a fix or gate is "real BP poles", not
B/f0.

Suggested pins: `CH_BP_n1_10-15kHz_g1_a0.1` (lost pole, narrow nominal band)
and `CH_BP_n1_100-2000Hz_g2_a0.1_abs` (exception, Chebyshev).

### 3.3 `origin_on_jw` is mostly a Highpass problem

19 designs: **14 Highpass** (all with absorb on, e.g.

representative case.

### 3.4 `2LPn-atten` search misses do not respond to search effort

`2LPn-atten` alone accounts for 996 of the 2 848 NO_BOM_SUSPICIOUS jobs (35 %).
Split by preset (≈1 050 jobs each):

| preset | OK | DEGRADED | NO_BOM_SUSPICIOUS | NO_BOM_ENVELOPE |
|---|---|---|---|---|
| Fast | 98 | 155 | 364 | 448 |
| Balanced | 125 | 170 | 324 | 408 |
| Thorough | 136 | 189 | 308 | 422 |

Thorough removes only ~5 % of the misses, and only ~12 % of all `2LPn-atten`
jobs end OK. The probe says that most of these fit the envelope, so this looks
structural (seeding / parametrisation of the R7 attenuator cell) rather than
"search harder". For all cells, NO_BOM_SUSPICIOUS by preset is
Fast 1 031 / Balanced 969 / Thorough 848, which points the same way. This is
input for FS-028 S2-4 step 2.

Other cells with notable "probe fits, no BOM" counts in the full run, not
visible in the standard sample: `2HPn-AM(+C1s)` 155, `2HPn-MFB2(+R7)` 128,
`2LPn-MFB-LS+R1(+R7)` 108, **`2LPn-unity` 86** (a unity-gain cell, so it is
not an attenuation problem), `2HPn-atten` 69.

### 3.6 Smaller observations

- **Equiripple-delay LP −3 dB corner off by 0.08 dB:** `ED_LP_n8_d5_1kHz_g1`
  and `ED_LP_spec-corner-stopband_d5_1kHz_g1_s40_last` show 3.09 dB at the
  1 kHz corner (warn). The standard run already showed it once; the 10-02
  report did not mention it. It looks like a −3 dB normalisation tolerance for
  n = 8.
- **`q_too_high`** (harness gate, Q > 100, topology not solved):
  `CH_BP_n5_1-1.2kHz_g2_a3` and `EL_BR_n5_1-1.2kHz_g10_a1_s40` (Q ≈ 100). The
  pairing and cascade checks pass. These are not app defects, but the harness
  does not cover cells at Q ≈ 100. Does the app warn about such sections?
  This was not checked.
- **Benchmark, Fast preset:** `LPn3-VCVS` gets no BOM with Fast, but Balanced
  and Thorough find one with cost 0.022. The other three no-BOM cases
  (`LPn2-VCVS`, `HPn2-MFB`, `HPn3-MFB`) fail on every preset, as in the FS-028
  baseline.
- **Numerical warnings in worker logs:** 218 × `filter_solvers.py:1450`
  "divide by zero" in `_F_raw_bp` (asymmetric BP), caused by evaluating exactly
  at a notch frequency. There are also 3 overflow cascades in
  `scipy.optimize._lsq`. Neither affected results. They are cosmetic, but they
  would hide a real warning.
- **Still never routed** even at full level: `2BP-AM2`, `2BP1LP-MFB`,
  `2BP1LP-MFB-QE`, `2LPn-gained+R7`, `3LPn-gained+R7`. The FS-028 benchmark
  solves `BP1LP-MFB` directly, so the cell works. Either the UI matrix never
  produces a BP1LP section, or routing never selects it. Check before calling
  these dead.
- Build: PyInstaller warns that the hidden imports `pycparser.lextab`,
  `pycparser.yacctab` and `scipy.special._cdflib` were not found. The bundle
  still works (exe health and `--selftest` pass). These are stale `hiddenimports`
  entries.
